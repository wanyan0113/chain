# 独立能力推理

本入口对应所提供截图2.1.1的式（1）及2.3步骤2、式（12）：从任务属性与显式的任务—能力映射规则，得到任务所需的能力集合。这里推导的是“任务需要什么能力”，不是“某件法器已经具备什么能力”。法器适用性筛选属于后续步骤3。

原文规则、构造输入、预期结论和实际结论的核对见 [能力推理原文对照](能力推理原文对照.md)。技术测试通过和两个入口一致均不代表完整文章复现正确。推理报告保存当时的独立副本，后续修改输入规则、来源或疑点不会改变旧报告。

## 运行

从项目根目录执行：

```powershell
.\.venv\Scripts\python.exe -B -m design infer-capabilities design/examples/capability_demo.json --output-dir generated/capability_demo
```

示例得到“对空具现能力”和“低空具现能力”。目标为法球时需要对空具现能力，来自截图 `联想截图_20261027150810.png` 的文字示例；低空能力类别来自表4，但示例中的500ft任务高度和1000ft分界均为虚构技术配置，不能作为文章案例数据或正式业务阈值。

输出为：

- `capability_report.json`：任务属性、所需能力、每条规则的逐条件结果、规则来源和阻塞项。
- `capability_summary.md`：中文可读报告。
- `capabilities.ttl`：仅在全部任务完整推理时输出；使用现有 `ArcaneMission`、三类能力及 `requiresCapability`，并附带任务—规则—结论证据。导出前与主本体合并做静态检查。

### 规范能力身份

独立能力入口通过 `capability_identity.py` 的显式登记表，将“角色＋结论名称”映射到主本体已有的规范能力URI，不进行模糊名称匹配。登记表覆盖当前表4的26个具名能力词项；测试核对每项的中文标签、具名个体声明及所属能力角色。修改规范词汇时须同步核对登记表。

报告的每项任务包含 `ontology_bindings`，记录 `status`（`mapped`／`unmapped`）、`canonical_uri` 和原因。例如已登记的“对空具现能力”导出时直接复用 `http://example.org/arcaneweb#AirManifestationCapability`。Markdown也显示对应URI；可直接按该URI查询 `requiresCapability`。

未知结论或角色不对应时，不自动合并：报告明确标记未映射，默认允许的局部导出会保留本次运行的局部个体，证据附有 `identityStatus` 和原因。未映射结果不宣称具有规范能力身份。

推理状态和身份映射状态分别报告，每项任务和报告顶层都有：

- `status`：当前规则下的推理状态，仍为 `complete`／`blocked`。
- `ontology_mapping`：`status` 为 `complete`／`incomplete`／`not_run`，并列出 `total`、`mapped`、`unmapped`。没有推出结论时为 `not_run`，不能以0/0声称通过。顶层计数按任务—能力对应项累计，同一能力在不同任务下分别计数。
- `canonical_export_ready`：只有推理完成且所有已推出能力都有规范对应时为true。部分已推出能力全部映射，仍不代表被阻塞的推理已完成。

需要严格使用规范URI时，使用以下入口：

```powershell
.\.venv\Scripts\python.exe -B -m design infer-capabilities design/examples/capability_demo.json --output-dir generated/capability_canonical --require-canonical
```

该模式不满足 `canonical_export_ready` 时保存JSON和Markdown报告、不生成RDF，退出码1；目录存在旧RDF时即使指定覆盖也会拒绝写入，要求换目录。Python对应 `capability_rdf(document, report, require_canonical=True)`，不满足时抛出 `DesignError`。默认不加参数继续支持已明确标注的局部个体导出。

映射计数、就绪标记和严格导出是项目的工程完整性约束，并非截图中新增的业务规则；它们不验证规则覆盖完备性，也不补造资料缺失的阈值。

运行、任务和逐规则证据仍有独立URI，多个任务可指向同一规范能力，证据分别关联各自任务；不添加 `owl:sameAs`，也不声明不同URI必然表示不同个体。这里完善独立能力导出的身份衔接，不改变任务条件、能力推理算法或旧完整设计导出入口。

退出码0表示给定规则范围内完整，1表示数据不足或所要求的角色未推出能力，2表示输入或输出错误。JSON写到标准输出。已有结果默认拒绝覆盖；可加 `--overwrite`。若目录已有成功RDF，本次又被阻塞，即便带覆盖参数也要求换目录，避免旧RDF与新失败报告混用。

## 输入

无需填写法器、具体目标编号、任务开始时间、协同边、评价指标和资源库存。最小输入见 `examples/capability_demo.json`，字段如下：

| 字段 | 含义 |
| --- | --- |
| `format_version` | 固定为 `1.0` |
| `scope` | 说明数据和规则的使用范围 |
| `required_roles` | 本次必须推出能力的角色；可选 `insight`、`coordination`、`manifestation`，至少一个 |
| `tasks` | 至少一项，包含唯一 `id`、`attributes`、`source_refs`、`blocking_issue_ids` |
| `task_rules` | 至少一条，与原完整设计流程的规则格式相同 |

任务可选带已有 `target`、`start_s`，但本步骤不使用它们。完整设计JSON可以提取上述字段，再明确指定 `required_roles`，作为独立推理输入。完整机器契约可通过 `design.capabilities.capability_schema()` 获取，它复用 `design/schema.json` 的任务属性、条件和规则定义，减少两个入口的格式差异。

规则包含唯一 `id`、`role`、`capability`、`when`、`source_refs`、`blocking_issue_ids`。一条规则只能引用 `task.xxx`；环境事实如要参与判断，需先明确其与任务的关联、时间适用性和处理依据，再作为带来源的任务属性提供。本入口不会自动选择环境观测或计算影响。

支持 `eq`、`contains`、`lt`、`le`、`gt`、`ge`。右侧使用字面量 `value` 或任务字段 `ref`，两者只能选一个。数值必须写为 `{"value": 500, "unit": "ft"}`，不接受裸数字；比较要求双方单位相同，本步骤不自动换算。

## 推理语义

一条规则的所有条件按合取判断：

```text
条件1 ∧ 条件2 ∧ … ∧ 条件n → 一项能力需求
```

- 所有条件成立且规则无阻塞疑点：`pass`，加入能力集合。
- 至少一项条件明确不成立：`fail`，该规则不推出能力，即使另一条件缺失也不会把整个合取误判为可能成立。
- 没有明确失败，但存在缺失、null、类型不符、单位不一致或规则疑点：`unknown`，整体报告被阻塞。
- `when: []` 表示明确配置的无条件规则，仍受规则疑点检查。
- 多条规则命中不同能力时全部保留；命中同一角色的同一能力时结论去重、逐规则依据仍保留。
- 任务存在阻塞疑点时，即使规则条件满足，整体仍为 `blocked`。
- `required_roles` 中任一角色未推出能力时报告 `NO_CAPABILITY`；不会自动补造默认能力。

`blocked` 报告中的已命中能力只是部分结果，不能作为完整需求传给后续法器筛选。`complete` 只表示当前输入和所配置规则范围内没有阻塞，不证明规则覆盖了所有实际需求。

截图中的近／远示例保留文字矛盾；用户已确认应为“目标近→近程能力”。独立示例不预置数值距离分界。已有完整技术演示沿用其注明的更正来源；定量分类仍需有依据的阈值和边界政策。

## Python与现有设计流程

```python
from design import infer_capabilities
from source_data.common import read_json

document = read_json('design/examples/capability_demo.json')
report = infer_capabilities(document)
if report['status'] == 'complete':
    requirements = report['tasks'][0]['required_capabilities']
```

完整设计 `design(document)` 和独立入口共用 `infer_task_capabilities`，两处使用同一条件解释和能力集合逻辑。完整设计仍要求三个角色；独立入口可以只研究具现能力等单一角色。

此处不新增外部推理器依赖，使用现有可解释的规则计算；HermiT继续承担可选OWL一致性检查。当前独立能力命令执行的是主本体静态兼容检查，未执行HermiT。

Excel首页执行案例导入与实例映射；另有 `/rules` 通用规则验证页面，支持上传规则Excel并显示结论、来源和对照结果，操作见 `../rule_review/使用说明.md`。它使用独立的通用条件验证实现，不调用本独立能力接口，不自动将来源案例转换成能力推理任务，也不将其结论回写本体。两种入口都能运行不代表文章规则已完整验证。
