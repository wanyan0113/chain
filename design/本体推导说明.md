# 本体推导参与链网设计

设计引擎现在在业务筛选前读取 `arcane_ontology.ttl`，沿命名类的 `rdfs:subClassOf` 关系推导法器类别。推导结果直接确定候选角色，也可作为业务规则条件；不再只是设计完成后的身份映射。

本次使用原本已有的类别公理，例如 `DecisionArtifact → CoordinationArtifact → Artifact`。不为演示另造文章没有给出的领域结论。新增法器子类时，在主本体声明 `owl:Class` 及其父类，无需修改Python分类分支；新增的类别应另行通过本体检查。

## 运行示例

```powershell
.\.venv\Scripts\python.exe -B -m design run design/examples/ontology_network_demo.json --output-dir tmp/ontology-network-demo --require-canonical
```

示例为虚构工程数据，来自原规范能力双任务示例，所有法器都只填写 `ontology_types`，不填写 `role`。协调法器声明为 `http://example.org/arcaneweb#DecisionArtifact`，程序推导其属于协调法器。其能力筛选规则额外要求推导类别包含 `CoordinationArtifact`，因此分类知识实际参与候选筛选。预计每个任务有两条候选链，网络检查四组组合、三组可行，选中一快一慢两条链。

`ontology_types` 填主本体中已声明的类的完整URI数组；多个类型必须共同导出唯一设计角色。未知类型、不能确定角色、跨角色类型或与显式 `role` 冲突均报输入错误。原有只填写 `role` 的输入仍支持，报告标记为显式角色输入，不将它说成子类推导。

规则可读取只读字段 `artifact.ontology_types`，用 `contains` 检查某类完整URI；该字段包含声明类及所有可达的命名父类。禁止在法器 `attributes` 中手填同名字段，避免伪造推导事实。来源疑点、可用性、数值条件及资源约束仍会参与判断。

## Excel与报告

原有专用或综合Excel无需增加列。在“法器”表的“角色”列，既可填探知、协调、具现，也可填本体类完整URI，多个用英文分号分隔。例如将协调法器改填 `http://example.org/arcaneweb#DecisionArtifact`。任务规则和法器规则表中的“角色”仍填原来的三种角色。

网页新增“本体分类推导”表；文字报告展示每个法器的输入方式、角色和分类路径。JSON的 `ontology_inference` 保存本体图摘要、声明类型、类型继承路径和来源；每个候选的 `ontology_evidence` 保存对应依据。选中法器的类型写入RDF，完整推导报告保存在已有的报告载荷中。

RDF导出会针对当前本体重新运行设计，拒绝被篡改的推导证据及本体变更前的旧报告。输入摘要仍针对原始输入，不因推导时增加角色而改变。

## 推理范围

这是明确限定的RDFS类型继承推导，不是完整OWL推理器。本次不执行等价类、匿名限制、属性链、SWRL或OWL全套一致性推理；不把存在性限制转换成某个具名能力，不从缺失关系推出否定结论。只加载本地主本体，遇到 `owl:imports` 拒绝继续，不隐式联网。

HermiT入口仍承担原有OWL一致性检查；设计网页及本次分类推导不会自动执行HermiT。任务→能力业务规则、表10比较、指标计算与网络优化继续由现有引擎执行。这一步证明本体分类可以成为设计输入，不表示原文完整案例已经复现，也没有把全部业务规则迁入OWL。
