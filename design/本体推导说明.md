# 本体推导参与链网设计

本文描述不带 `knowledge` 的兼容模式。新知识协作模式实际调用HermiT，支持等价类、限制表达式及具名结果回流。下文“不执行等价类”“不会自动执行HermiT”等仅指兼容模式，见 [知识协作说明](../knowledge/README.md)。

设计引擎在业务筛选前读取 `arcane_ontology.ttl`，沿命名类的 `rdfs:subClassOf` 关系推导法器类别，并执行对象属性的子属性、逆关系和对称关系推导。结果用于候选角色确定、能力规则条件和成链检查。

本次使用原本已有的类别公理，例如 `DecisionArtifact → CoordinationArtifact → Artifact`。不为演示另造文章没有给出的领域结论。新增法器子类时，在主本体声明 `owl:Class` 及其父类，无需修改Python分类分支；新增的类别应另行通过本体检查。

## 运行示例

```powershell
.\.venv\Scripts\python.exe -B -m design run design/examples/ontology_network_demo.json --output-dir tmp/ontology-network-demo --require-canonical
```

示例为虚构工程数据，来自原规范能力双任务示例，所有法器都只填写 `ontology_types`，不填写 `role`。协调法器声明为 `http://example.org/arcaneweb#DecisionArtifact`，程序推导其属于协调法器。其能力筛选规则额外要求推导类别包含 `CoordinationArtifact`，因此分类知识实际参与候选筛选。预计每个任务有两条候选链，网络检查四组组合、三组可行，选中一快一慢两条链。

`ontology_types` 填主本体中已声明的类的完整URI数组；多个类型必须共同导出唯一设计角色。未知类型、不能确定角色、跨角色类型或与显式 `role` 冲突均报输入错误。原有只填写 `role` 的输入仍支持，报告标记为显式角色输入，不将它说成子类推导。

规则可读取只读字段 `artifact.ontology_types`，用 `contains` 检查某类完整URI；该字段包含声明类及所有可达的命名父类。禁止在法器 `attributes` 中手填同名字段，避免伪造推导事实。来源疑点、可用性、数值条件及资源约束仍会参与判断。

## Excel与报告

原有专用或综合Excel无需增加列。在“法器”表的“角色”列，既可填探知、协调、具现，也可填本体类完整URI，多个用英文分号分隔。例如将协调法器改填 `http://example.org/arcaneweb#DecisionArtifact`。任务规则和法器规则表中的“角色”仍填原来的三种角色。

网页新增“本体分类推导”表；文字报告展示每个法器的输入方式、角色和分类路径。JSON的 `ontology_inference` 保存本体图摘要、声明类型、类型继承路径和来源；每个候选的 `ontology_evidence` 保存对应依据。选中法器的类型写入RDF，完整推导报告保存在已有的报告载荷中。

RDF导出会针对当前本体重新运行设计，拒绝被篡改的推导证据及本体变更前的旧报告。输入摘要仍针对原始输入，不因推导时增加角色而改变。

## 推理范围

这是明确限定的类型继承和属性公理推导，不是完整OWL推理器。不执行等价类、匿名限制、属性链、传递属性、SWRL或OWL全套一致性推理；不把存在性限制转换成某个具名能力，不从缺失关系推出否定结论。只加载本地主本体，遇到 `owl:imports` 拒绝继续，不隐式联网。

HermiT入口仍承担原有OWL一致性检查；设计网页及本次推导不会自动执行HermiT。任务→能力业务规则、表10比较、指标计算与网络优化继续由现有引擎执行。本体分类及关系已成为设计输入，但原文完整案例仍未复现，也没有把全部业务规则迁入OWL。

## 能力与协同关系推导

新增可运行示例：

```powershell
.\.venv\Scripts\python.exe -B -m design run design/examples/ontology_relations_demo.json --output-dir tmp/ontology-relations-demo --require-canonical
```

示例全部为虚构工程配置，使用已有本体公理：

- `能力 realizedBy 法器` 经 `hasCapability owl:inverseOf realizedBy` 得到 `法器 hasCapability 能力`。
- `协调法器 coordinationToManifestationCommunication 具现法器` 经子属性关系得到一般传讯关系。
- 已声明的一般传讯关系，经 `communicatesWith` 的对称性得到反向的一般传讯关系；不反向推导专用子属性，不推导跨中继的可达通信。
- `协调法器 orchestrates 具现法器` 为显式统筹事实。传讯本身不能推出统筹。

JSON输入增加可选 `ontology_relations` 数组，每项格式如下。主体和客体的 `kind` 为 `artifact` 或 `capability`，前者 `id` 引用本次输入法器编号，后者引用主本体中的能力个体完整URI。`predicate` 必须是已声明的对象属性，并能推导到具备能力、一般传讯或统筹关系。来源不能为空。

```json
{
  "subject": {"kind": "capability", "id": "http://example.org/arcaneweb#RapidResponseCoordinationCapability"},
  "predicate": "http://example.org/arcaneweb#realizedBy",
  "object": {"kind": "artifact", "id": "demo-coordinator"},
  "source_refs": ["已确认的资源能力清单"],
  "blocking_issue_ids": []
}
```

规则可使用 `artifact.ontology_capabilities contains 能力完整URI`。这是已知正向事实集合：没有得到某项能力关系时，该检查为 `unknown`，不因为“未记录”就断言“不具备”。此保留字段不允许在法器属性中手填。已知能力也不能绕过任务目标类型、距离、高度、来源疑点、可用性、库存等条件，必须与适用的业务规则合并核验。

协同距离行仍保留 `from`、`to`、`distance`、`max_distance`、来源和疑点。`communicates` 或 `controls` 填 `null`（也可省略）表示请求使用本体事实：推导到对应关系才置为 `true`，否则保持未知并阻塞可能可行的方案。显式 `false` 与正向推导冲突会报错；已有 `true/false` 输入仍支持。不由关系事实生成缺失的距离、阈值或协同距离行。

带 `blocking_issue_ids` 的关系声明保留为未知，不进入可用事实集合。所有声明仍做引用、属性声明、能力角色及命名定义域/值域的结构检查。这些端点检查是本工具的输入要求，不是声称OWL会把缺少类型当作逻辑矛盾。关系推导最多生成100000项事实；超限报错，不截断后继续宣称设计完成。

### Excel可选工作表

原专用及综合工作簿可增加“本体关系”表，列名依次为：`主体类型、主体、关系URI、客体类型、客体、来源、阻塞疑点`。主体/客体类型填“法器”或“能力”；能力填完整URI，法器填已有编号。无此表的旧工作簿继续兼容。

“协同关系”表的“传讯”“统筹”列可填文本 `本体推导`，距离和最大距离照常填写。规则条件表中按常量比较读取 `artifact.ontology_capabilities`，比较值为能力URI。综合来源查询页验证可选表结构，但不执行设计推导。

### 推导证据与导出

`ontology_inference.relations` 保存声明及其疑点状态、每项可用事实的来源、使用的实际本体公理、前提事实、法器能力集合和协同判断的使用记录。网页显示关系依据表及完整记录，文字报告列出关系与来源。RDF写入选中法器相关的正向事实及推导关系；未选中法器的关系只在报告中保留。导出重算同时保护分类和关系证据。
