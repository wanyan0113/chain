## 主要差异

### 1. 映射程序没有接入主本体

`maintenance_demo/mapping/run_mapping.py:16` 使用 `https://example.org/maintenance#` 命名空间；第 28—31 行仅加载该目录的 `schema.ttl` 和输入，未加载 `killweb_ontology.ttl`。

主本体使用 `http://example.org/killweb#`，资源能力关系是 `hasCapability`；维修例子使用 `providesCapability`。程序没有在两个词表间建立映射。因此当前结果是维修规则演示，不能直接读取主本体中的任务/装备得到截图中的设计结果。这是当前演示的范围边界，不是已经完成领域接入。

### 2. 两级结构对应，但具体条件和边界并不相同

`task_rules.rq:10` 起使用设备种类、任务种类和留档标记推导检测/记录/维修能力。它与式（1）的“条件合取 → 能力”结构一致，但不是截图中的领域条件。

`resource_rules.rq:9` 起使用“存在非空需求、一个资源覆盖全部能力、显式可用、响应不超限”筛选。截图式（2）示例涉及多项性能条件；当前只验证了一项数值比较以及能力集合覆盖。

尤其是第 13 行为 `response <= limit`，而截图中的示例写的是严格小于/大于。这不是逐条翻译原文。当前测试还明确规定等于响应上限时允许成为候选。不能为了声称一致，就把这个自定义维修政策描述为来源原文。

“单个资源覆盖全部能力”也是演示假设。截图提到“一组法器”，并未明确所有所需能力必须由同一个实体提供，因此当前演示并未验证多资源联合覆盖的问题。

### 3. 2.1.2 和 2.1.3 尚未在本轮规则实现

主本体中已经有通信、指挥、链节点、链间组合等词汇，但属性存在不代表已经执行条件判断。

当前已提交的映射入口不验证截图 2.1.2 的关系可行性，也不生成法术链；不验证 2.1.3 的共享、时间间隔或消耗性资源使用约束，也不聚合成网。三个任务和三个候选关系不能当作已完成的三条链。

### 4. 本体中的公式记录准确，但没有被执行

`killweb_ontology.ttl:1765` 起的 Formula01—Formula10 与截图数学表达式逐项对应。式（1）—（3）用 AND 文本表达合取；式（4）—（10）的求和、乘积、归一化方向和加权形式均记录正确。

这些表达式保存在 `formulaText` 注解中。映射运行器没有读取或计算这些注解，也没有生成 T/A/C、归一化值或 P。当前可以称“公式已记录”，不能称“评分算法已实现”。

### 5. 本地旧优化器与截图的评分公式不同

`maintenance_demo/optimize_workflows.py:116` 定义的是按参考值缩放的时间、成本、风险加权和；第 180 行选择得分较小的方案。

截图式（7）—（10）使用比较集合的 min/max 归一化，指标为时间、精度、成本，P 越大越好。旧脚本使用的风险与截图精度不是已定义的同一指标，参考值缩放也不同于 min/max 归一化。

旧脚本第 85 行按活动时长乘费用率计成本，第 86 行累乘成功概率；这些是维修模型的设定，不能仅因有求和或乘积就断言与表 6 的三个阶段指标相同。该文件当前未被 Git 跟踪，不在本轮已推送实现中；本次只作静态比对，未运行旧优化器。
