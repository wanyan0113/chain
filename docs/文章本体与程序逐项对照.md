## 总体结论

`killweb_ontology.ttl` 0.7 已表达文章核心概念、分类、属性与关系，并保存公式说明。可执行部分使用独立维修模型，已具备事实校验、两级映射、协同验证、参与记录、网络关系与描述性统计。

两者是“来源模型的结构整理”与“非武器方法验证”两项交付。维修程序没有加载主本体，没有建立二者的等价类或等价属性，也没有完成文章领域系统。不能用维修程序通过测试证明主本体已经能够生成实例链网。

## 维修场景的模型与运行衔接

这一场景已经使用统一命名空间 `https://example.org/maintenance#`，无需再造一套词表或通过替换中文标签来接入规则。

| 层次 | 权威输入或产物 | 责任 |
| --- | --- | --- |
| 基础词表 | `mapping/schema.ttl` | 维修任务、资源、能力及映射规则标识 |
| 协同扩展 | `collaboration/schema.ttl` | 流程请求、依赖、参与记录、组合、容量及耗材 |
| 原始事实 | `collaboration/input.ttl` | 任务条件、资源事实、依赖、授权、格式和固定窗口 |
| 质量约束 | 两目录的 `input_profile.json` | 数量、类型、范围及依赖环等输入要求 |
| 推导结果 | `requiresCapability`、`candidateResource`、`canHandoffTo` | 由规则生成；原始输入不可预填 |
| 验证后产物 | Workflow、Execution、WorkflowNetwork 及关系 | 程序建立参与记录并导出；不是 OWL 类声明自动实例化 |
| 描述性统计 | 网络历时、工时、容量利用率及耗材余量 | 对同一次已验证计划计算，不从旧报告拼接 |

当前任务依赖不由程序猜测，时间窗口也不由响应时间换算。`responseMinutes` 是响应筛选量，`durationMinutes` 是执行时长；二者保持独立。

## 顺序与验收

1. 完成对照：本文件给出声明、执行和缺口，保留来源不确定性。
2. 贯通维修案例：统一入口从同一批原始事实运行现有规则、协同和统计，导出本次输入/模式/配置/规则指纹。
3. 生成解释：已逐任务列出命中规则、能力需求、候选与实际资源，逐交接列出授权及公共格式；补充响应、时间间隔、容量、耗材数值对照，并在可读报告中展示失败原因及最多五个组合示例。
4. 展示与指标：输出可读案例说明及维修网络关系图；质量、计价等未定义的数据明确列为缺失。

贯通入口与复现方式见[维修完整案例](维修完整案例.md)。上述验收只针对维修示例。主本体的结构核对、来源整理与维修模型的执行验证分别记录；不实现武器选择、攻击链生成或作战评分优化。
