# 跨流程候选链联合优化技术设计

基线编号：TFDO-DESIGN-1.0。冻结日期：2026-11-28。状态：设计评审通过并冻结，尚未开发或验收。依据：本轮用户确认的设计与补充评审意见。

本阶段扩大活动流程和法器分配的联合决策空间，在保持现有资源约束与评价目标语义的前提下，使同一任务的不同活动流程产生的候选链参与统一评价和跨任务组网。冻结设计不表示功能已经实现，也不表示精度模型已经获得业务有效性证明。

配套文档：[开发任务](development-v1.md)、[验收矩阵](acceptance-v1.md)。现有实现边界见[真实法器组网桥接](../design-bridge.md)。

## 1 当前基线与升级范围

现有桥接器搜索一组活动流程，调用真实design完成本体推理、法器链生成、跨任务约束检查和网络优化；找到首个资源可行流程组合后停止。现有网络目标为所选链评分的平均值，已经同时检查容量、库存、冷却、连接、任务依赖及开启时的表10约束，不是独立选择各任务最高分后简单求平均。

保留现有快速入口和行为。新增模式设计名为 `joint_candidate_optimization`；现有快速行为在新接口中标识为 `first_resource_feasible`。名称是待开发接口约定，不代表当前CLI已经支持这些参数。

本阶段仍限定有限活动、有限对象、确定性效果、有界顺序搜索、显式活动映射、每环节一个法器和固定任务开始时间。不能通过补假活动或占位指标绕过旧设计契约。自然语言/API、同环节多法器、自动调度、真实执行、动态重规划、FDNA和所有无界任务的全局优化均不在本阶段。

## 2 搜索对象

| 对象 | 语义 | 区分规则 |
| --- | --- | --- |
| 活动流程 | 有序活动实例及其语义 | 活动身份、版本、参数或顺序不同，即不同流程；同终态不合并 |
| 候选链 | 一项任务的活动流程及逐环节法器绑定 | 同流程换法器、不同流程用同一组法器均不同 |
| 候选网络 | 为每项任务联合选取一条候选链及其关系 | 受跨链资源、时间、依赖及协同约束限制 |

活动实例保留完整参数，不只保留目标。桥接首版仍可明确拒绝不支持的参数结构，但不得丢弃额外参数后合并身份。重复活动按序列位置区分，不能使用角色或活动ID作为唯一分配键。

## 3 模块职责与运行阶段

| 模块 | 责任 | 主要输出 |
| --- | --- | --- |
| A 输入与上下文 | 校验并冻结任务、活动库、知识、资源、映射和政策 | 输入快照、上下文摘要、运行身份 |
| B 活动搜索 | 生成多流程、独立重放、标识流程、报告覆盖 | 验证通过的流程与逐任务搜索证据 |
| C 候选链生成 | 真实推理、映射、分配、连接及单链资源核验 | 未排名的候选链和原始证据 |
| D 集合管理 | 候选身份、去重、来源追踪、按任务汇总 | 冻结候选集合及集合摘要 |
| E 统一评价 | 原始指标、归一化、权重、政策版本 | 链指标、归一化值、评分及证据 |
| F 联合优化 | 从各任务集合选链，执行跨任务约束与搜索 | 可行网络、目标值和最优性证据 |
| G 独立验证 | 重放流程、复算指标、核验资源、RDF和结论范围 | 验证报告、设计文件和证明状态 |

严格执行：候选生成 → 集合冻结 → 统一评价 → 联合优化 → 独立核验。生成过程中可以记录原始指标，但不得把临时极值下的分数当成最终评分用于不可逆淘汰。

若增加候选，建立新的集合版本，重新评价和优化；旧集合、旧分数与证据保留，不就地混合。预算导致候选不完整时，可以显式冻结已生成的合格子集并优化，但不能因此声明边界内全局最优。

## 4 三类身份

### 4.1 candidate_id

候选链稳定身份。相同语义载荷、执行上下文和身份规范版本应得到相同ID。建议计算结构为：

```text
candidate_id = SHA256(canonical({
  identity_version,
  task_id,
  task_context_hash,
  flow_id,
  activity_instance_sequence,
  artifact_assignment,
  design_context_hash,
  knowledge_snapshot_hash,
  mapping_hash
}))
```

结构化载荷留存，不能只留下不可解释的哈希。`artifact_assignment`为有序数组，包含step_index和artifact_id；不得以角色名或可重复活动名为唯一键。

### 4.2 run_id

一次具体执行的独立身份，使用UUID等唯一生成机制。即使输入完全相同，两次执行也必须具有不同run_id。运行时间、预算、算法版本、平台信息、搜索轨迹和终止原因归入运行记录，不因此改变候选链身份。

### 4.3 candidate_evidence_id

候选在某次运行中的一次生成或验证证据身份。至少绑定run_id、candidate_id、证据类型、证据序号、分析器/验证器版本和证据内容摘要。同一个候选可对应多个证据记录，内容相同也不跨运行丢弃证据。

候选实体与证据采用一对多关系。来源流程、映射、规则命中、原始指标政策和验证结果均通过证据关联，不能用去重删除历史记录。

## 5 哈希字段边界与规范化

所有模块使用同一个版本化规范化入口和字段投影定义，不各自拼接字符串或另行近似规范化。

| 摘要 | 必须覆盖 | 排除 |
| --- | --- | --- |
| task_context_hash | 任务/目标身份、属性、开始时间、规划初始与静态事实、目标、必须活动、禁用条件、活动次数等业务约束 | 显示名、输出路径、节点/时间/候选预算、搜索模式、发现顺序 |
| flow_id | 有序活动ID、版本、完整绑定参数、目标参数标识，以及所使用活动的语义摘要 | 显示编号、搜索轨迹、最终状态作为唯一标识 |
| 活动语义摘要 | 所使用活动的参数声明、适用条件、前置条件、效果、能力需求、次数约束及相关事实/派生规则定义 | 单纯生成编号；仅靠可被错误复用的版本号 |
| design_context_hash | 冻结场景中的法器类型、属性、可用性、指标、容量、库存、冷却、全部上下文、连接、资源组和任务依赖 | 生成后的评分、排序、节点访问数、输出位置 |
| knowledge_snapshot_hash | 基础本体、规则、事实映射及明确加载的知识文件精确快照摘要 | 由本次流程派生的临时模板名称和排名 |
| mapping_hash | 活动身份/版本到角色、活动、能力和连接策略的显式映射、能力阈值、复用策略及版本 | 无语义的映射显示编号 |

首版design_context_hash保守地覆盖完整场景资源上下文，不尝试推断“无关资源”。因此，其他资源的变化也可能使现有候选上下文身份变化；这是有意采用的保守失效策略，后续若采用依赖切片须升级身份版本。

基础知识快照采用精确文件快照策略：文件字节变化可以使身份变化，即使OWL逻辑含义未变。规范化只承诺相同规范载荷可复现，不承诺识别所有逻辑等价知识。仅改变候选输出的显示编号不改变候选身份；改变基础知识文件中的标签可能改变知识快照，两者不能混为同一个测试。

派生的sequences_inline独立保存内容摘要和生成证据，不把其生成序号反向写入基础知识摘要形成循环身份依赖。评价模型版本、权重、归一化集合和排序规则归入评价证据，不写入候选实体身份。

对象键顺序统一；活动、参数列表中具有业务意义的顺序保留；明确定义为集合的字段按规范键排序。字符串采用统一Unicode规范并检查键冲突。数值有限、单位显式，不自动换算；身份数值采用固定的版本化JSON数字表示规则，统一处理负零，禁止NaN和Infinity，避免整数精度丢失。保留原始输入作为证据，不能只保留规范结果。

## 6 去重与一致性

1. candidate_id相同且规范载荷一致：合并候选实体，追加全部证据。
2. ID相同但载荷不同：报告身份冲突，阻塞相关集合，不默默覆盖。
3. 同候选、同原始指标政策下计算出不同指标：报告证据不一致，阻塞评价。
4. 指标政策改变时，允许同候选产生不同版本的指标证据，但不能混入同一评价集合。
5. 不因相同终态、相同角色序列、相同资源成员集合或相同评分合并候选。

固定输入下候选发现顺序可以不同，最终规范集合摘要应一致；证据序号、run_id和运行耗时可以不同。

## 7 候选集合与归一化

对任务k定义：

\[
\mathcal C_k=\bigcup_{f\in\mathcal F_k}\mathcal C_{k,f}
\]

其中C(k,f)由通过流程重放、映射、能力、连接及单链资源核验的候选链构成。跨任务联合冲突在F阶段处理，不预先要求每条链已知可参加一个完整可行网络。集合必须包含具有完整可评价指标的成员；已纳入候选若指标缺失，不以0.5、1或原文案例值补齐，相关评价阻塞并报告原因。

冻结记录至少包括：任务ID、规范候选ID有序列表及哈希、原始指标政策、生成覆盖范围、未知与不支持项、搜索预算和终止原因。候选计数区分原始生成数、去重后数量和证据数。

每个任务分别在其跨流程集合内取极值，沿用时间/成本越小越好、精度越大越好的极差归一化：

\[
T'=\frac{T_{max}-T}{T_{max}-T_{min}},\quad
A'=\frac{A-A_{min}}{A_{max}-A_{min}},\quad
C'=\frac{C_{max}-C}{C_{max}-C_{min}}
\]

任一指标max=min时，其所有候选归一化值固定为0.5。单候选同样处理；空集合不进入评分。首版沿用现有有限浮点计算及精确相等判断，不引入未声明的isclose阈值；后续改变算术或容差必须升级政策，并与参考计算对照。

加入极端候选可能改变既有候选的归一化值和综合排序，但不保证每个值都改变。例如时间10、20加入100，最短10的时间分仍是1，20的时间分由0变为8/9。这是极差归一化的集合依赖，不是实现错误。

链评分：S=wT*T'+wA*A'+wC*C'。权重、退化规则、算术版本、集合摘要和极值共同构成normalization_scope/evaluation_context。不得直接比较不同集合单独归一化的历史分数。

## 8 原始指标政策与独立验收

新增联合模式必须显式选择政策，不能根据历史默认值猜测。拟采用的多环节原始指标政策标识为 `sequential_product_v2`：

\[
T=\sum_iT_i,\qquad A=\prod_iA_i,\qquad C=\sum_iC_i
\]

该标识是待实现的版本化政策声明；现有sequential_product和insight_lock_product不因此改名、删除或改变默认值。v2在此设计中规定含义与证据边界，不声称公式相比现有连乘模式有新的理论证明。

活动指标按实际执行次数计，阶段指标不能重复包含上游过程；单位一致。accuracy必须解释为可采用乘积组合的无量纲精度/质量系数，不自动解释为概率。拆分同一活动不能无依据地重复赋整个过程的精度。增加一个小于1的协调因子会降低乘积，该模型不自动刻画解析带来的增益。

政策至少分开记录：raw_metric_policy、normalization_policy、chain_weight_policy和network_objective_policy及其版本。原始公式实现正确性与业务有效性分开验收：手算一致可以标implementation_verified；对多协调环节的实际含义尚需领域实验，domain_validity保持pending，不能因软件测试通过改为proven。

## 9 联合网络优化

本阶段保持网络目标：

\[
\max\frac1K\sum_{k=1}^{K}S_k(c_k),\quad c_k\in\mathcal C_k
\]

每任务必须选一条，资源容量、库存、冷却、资源组、任务依赖、连接和开启的表10检查继续生效。所有任务数量固定时，平均值与总分最大化等价。完成跨度和总成本仍输出，但不是额外直接优化目标；任务优先级、公平性或新目标须另行设计。

不先按流程筛选唯一最高分链。允许安全的能力/连接/单链资源排除；默认不做仅基于指标的跨资源支配删除。任何新的候选支配或上界剪枝，必须同时考虑资源、时段、约束和归一化极值语义，并用独立小规模穷举验证。

候选生成完整不代表网络枚举完整；网络访问不完整也不代表无法证明最优。可靠分支定界可以证明未访问分支不可能改进。保存完整集合或足够的可复核界限证据，不能用“没搜到更好”代替证明。

## 10 结论与异常处理

| 结论 | 条件 |
| --- | --- |
| feasible | 至少一网通过独立资源核验，最优性可能尚未证明 |
| fixed_flow_optimum | 固定流程组合下网络优化完成证明 |
| candidate_set_optimum | 冻结候选集合中网络优化完成证明 |
| bounded_global_optimum | 声明范围流程与链生成覆盖完整，相关未知/不支持已解决，且网络优化完成证明 |
| candidate_set_infeasible | 完整核验或可靠剪枝证明冻结集合不能组网，不推断所有未生成流程无解 |
| bounded_global_infeasible | 所有声明范围覆盖及约束证明完整，没有妨碍结论的未知 |
| undetermined | 未知、不支持、验证不一致、指标不完整或其他不足以证明的情况 |

流程、链生成预算超限允许显式冻结已生成合格子集并继续，但同时保留partial覆盖和具体终止原因。网络优化超限若有独立验证通过的当前最好解，只能标feasible/incumbent，不能标candidate_set_optimum；不得伪装旧design的complete/proven结果绕过导出门槛。无可行解且超限为未定，不是无解。

输入或知识在一次运行期间变化时停止并标context_changed，不复用旧拒绝或评分。任一任务没有可评价候选时，不将其从任务集合删除后优化平均值。已知集合最优不等于边界内全局最优；未知分支不影响已知子集定义，但阻止无依据的全域结论。

## 12 冻结与变更

本目录v1设计、任务拆分及验收矩阵共同作为基线。内容摘要由manifest-v1.json保存，不包含该清单自身。更改身份边界、目标函数、候选域、归一化或原始指标语义必须通过显式设计变更，更新版本、变更原因及受影响验收项，不静默改写本基线。

冻结只代表用户认可的技术设计方向。现有程序仍采用首个资源可行流程组合策略；新模式、三类身份管理和全局覆盖证明尚未实现。后续开发不能把本文件中的拟定字段或政策版本表述为当前功能。
