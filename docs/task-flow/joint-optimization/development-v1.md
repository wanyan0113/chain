# 跨流程联合优化开发任务

依据：[TFDO-DESIGN-1.0](design-v1.md)。状态：计划，未开始编码。每项完成须具备接口、独立预期、反例、证据和范围说明；软件实现与业务模型验证分开。

## 1 模块任务与依赖

| 工作包 | 内容 | 交付与通过门槛 | 依赖 |
| --- | --- | --- | --- |
| WP-A 上下文管理 | 输入投影、公共规范化、版本化哈希、知识冻结、运行身份 | 明确字段白名单/集合排序规则；身份可复现；输入变化检测；不修改输入 | 无 |
| WP-B 多流程搜索 | 复用SearchSession、独立重放、确定性flow_id、逐任务覆盖报告 | 顺序和完整参数保留；语义变化影响身份；边界/未知/超限不混淆 | A |
| WP-C 未排名候选链生成 | 从当前design提取或增加生成接口，接收多个验证流程 | HermiT实际运行；候选保留完整分配、原始证据及单链约束；不先选每流程最优 | A、B |

基础模块可解耦实现，但需按依赖集成；本设计不自动授权子代理、并行开发或修改旧实验。

## 2 推荐开发顺序

1. 先实现上下文与身份规范，固定测试向量，避免后面变更身份破坏全部证据。
2. 提供只生成候选链、不做最终评分/选择的design接口，并与旧路径候选覆盖对照。
3. 接入多流程和独立重放，完成按任务汇总、去重及冻结。
4. 在冻结集合上实现版本化评价，与手算参考核对。
5. 接入已有跨任务约束搜索，与完整笛卡尔积参考对照最优值、可行性和确定性同分选择。
6. 最后接CLI、RDF和完整报告，测试部分搜索、未知和上下文变化。

不能先把各流程各自评分的最高分链接到一起，再补统一评价；这会提前丢失候选。

## 3 拟定接口边界

接口名称待编码落实，职责冻结如下：

```text
freeze_context(inputs) -> context_snapshot
search_and_verify_flows(context, limits) -> flow_records + coverage
generate_unranked_chains(context, flow_records, limits) -> chain_occurrences + coverage
identify_and_merge(chain_occurrences) -> candidates + evidence_records
freeze_candidate_sets(candidates, coverage) -> candidate_set_snapshot
evaluate_candidate_sets(snapshot, policies) -> evaluation_snapshot
optimize_network(evaluation_snapshot, context, limits) -> network_result + proof_scope
verify_and_export(network_result, snapshots) -> verification + artifacts
```

各接口采用明确版本、不可变快照或深拷贝，返回值区分候选实体、运行证据、评价结果和证明范围。源规则/知识哈希与相关政策版本贯穿全过程，输出不得依赖临时全局模板文件。

## 4 实验与验收交付

- 固定输入夹具：同任务多流程、同流程多法器、资源冲突、重复活动、多参数身份、极端指标、退化指标、未知及超限。
- 独立参考：小规模活动序列与候选链完整枚举，独立指标复算和网络组合核验；避免仅调用被测评分/资源检查器得到预期。
- 证据目录：源输入、快照、候选载荷、证据记录、集合极值、网络搜索/剪枝、独立验证、RDF和汇总。
- 旧行为回归：task_flow逻辑规划与重放、通用服务接口、原快速桥接、磁盘/内联模板、原有评价模式、表10、网络搜索和设计入口。
- 模型验收：sequential_product_v2的编码正确性可自动测试；协调精度含义及环节拆分合理性需独立领域样例或数据，未完成时不得标为业务验证通过。

## 5 完成定义

完整实现须通过[验收矩阵](acceptance-v1.md)，并提供一组确实优于首个可行策略的小规模案例：在相同业务输入、原始指标定义、统一评价基准及约束下，首个可行流程未选中的另一个流程参与候选池后产生更优可行网络。不能将不同归一化集合中的旧分数直接相减宣称提升。

性能实验单独报告节点数、候选规模、峰值内存、端到端时间及预算。准确性测试通过不等于效率提升；不能从小规模结果外推任意大规模性能。
