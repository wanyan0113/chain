# 阶段二受控性能实验

设计遵循[实验协议](protocol.md)，结论及逐档数据见[基线报告](results-v1/README.md)。阶段一已按用户评审关闭，JV-AUDIT-001继续保留为已修复审计发现。

入口：

```powershell
.\.venv\Scripts\python.exe -B -m workflow_tools.benchmark_joint --output-dir generated/task-flow/my-stage2 --repetitions 5
.\.venv\Scripts\python.exe -B -m workflow_tools.report_joint_benchmark --source generated/task-flow/my-stage2 --output-dir generated/task-flow/my-stage2-report
.\.venv\Scripts\python.exe -B -m unittest tests.test_joint_benchmark
```

输出目录必须不存在。可用重复的 `--case` 参数选择档位；硬件查询受限时可用 `--hardware-json` 指定已核对的CPU/内存JSON。每次重复新建工作进程，绝不以重复运行次数作为持久JVM热启动次数。

## 本轮观察

18档各5次，共90次有效运行，所有档位的重复语义摘要一致。7项工具测试通过，包括实验轴有效性、目录摘要、输入保持及加测量/普通运行一致性。完整可行案例均经独立参考对照；两个无解案例分别穷举1024和64个组合，没有找到可行网。

- P1实际流程1/2/4条，对应唯一候选链4/8/16条；总时间中位数约3.214/3.533/3.734秒。
- P2法器复制倍数1/2/3，对应候选链4/32/108条；总时间中位数约3.408/3.351/3.484秒。这个规模下时间波动与固定推理成本占比较高，不能从第二档更快推导出负增长或加速收益。
- 多数档位的OWL调用约2秒，当前联合网络搜索通常只有数毫秒。优先值得进一步拆测的是OWL适配器、进程/JVM启动与推理本身的成本，而非立即改网络优化算法。
- 网络节点预算8产生了核验通过的可行解，独立事后参考计算分数差距为0；生产端仍正确报告 `not_proven`。碰巧已找到最优解与已经完成最优性证明是两回事。

当前没有缓存、并行或增量算法的性能收益结论。下一步应先细化推理内部计时，并以更大且仍可解释的场景寻找退化点；精度政策的领域实验另列阶段三。

## 实施中遇到的问题

早期P1构造器更新活动库后漏更新请求中的目录摘要，生产系统正确拒绝请求。已经修复构造器，并增加所有实验活动库与请求摘要一致性检查。首批15次P1拒绝运行被排除，修复后独立补跑15次；首批其他档位的测量逻辑与输入没有修改。归档保存原测量工具源码、原环境、失败原因与修复后环境，不用新工具摘要覆盖旧批次。

上述补跑汇总时还发现：T1原先不要求解析，增加解析活动并未实际增大流程集合。因此该补跑15次也不参与有效基线，改为显式启用解析需求，并再跑1/2/4个实际流程各5次。新增规划测试与运行时断言验证实际流程数；报告工具同时检查解析需求与流程数量，防止“配置档位变了，实际问题规模没变”。有效基线仍为90次，另有30次P1运行被排除并保留批次记录。

早期采样工具使用按字典内容删除嵌套测量栈，可能删除相同内容的外层观测，已改为严格按栈顺序退出。该问题在正式测量批次启动前修复，预跑数据不用于基线。没有因此修改业务验证器或优化器。

原环境硬件查询被沙箱拒绝，日志如实保留；随后经授权读取CPU与物理内存并另存hardware.json，未伪造硬件字段。

## 解释边界

本轮是有限规模、同一主机、带测量开销的基线。阶段计时能区分当前流程搜索、候选生成（含OWL）、OWL调用、网络搜索及独立核验，但OWL内部未进一步区分JVM启动与纯逻辑计算。未知的细分指标保持未测量，不能据此断言HermiT算法本身占用了全部OWL调用时间。

无解案例补充独立全空间穷举对照；有可行解的完整案例使用既有独立排列/组合参考。网络预算为8的当前最好解另行按同一候选集合计算差距，独立参考的事后结果不会把生产端的 `not_proven` 改成已证最优。

阶段三仍需真实或有明确误差机制的受控数据检验 `sequential_product_v2`。本轮性能数据不能证明乘法精度模型的业务有效性，也不能替代一环节多法器融合模型。
