# 维修完整案例

2026-10-24。按[逐项对照表](文章本体与程序逐项对照.md)整理独立维修模型的统一运行入口，复用现有规则和验证器，不改变两级映射、交接或资源政策。

## 一次运行

在仓库根目录执行：

```powershell
.\.venv\Scripts\python.exe -m maintenance_demo.collaboration.run_case
```

主要代码为 `maintenance_demo/collaboration/run_case.py`。入口从 `collaboration/input.ttl` 加载维修事实，并合并基础和协同词表，调用原有程序完成：

**输入校验 → 需求和候选推导 → 交接推导与协同验证 → 参与记录与网络 → 统计与解释。**

依赖仍是 `requirements.txt` 中已有的库。没有增加新的领域模型、近义词匹配、任务自动分解或最优排程。

## 导出内容

默认目录为 `maintenance_demo/collaboration/generated/case/`：

| 文件 | 内容 |
| --- | --- |
| `validated_workflows.ttl` | 本次验证成功后生成的流程、参与记录和网络关系 |
| `merged.ttl` | 维修模式、原始事实、推导和验证后结果的合并图 |
| `case_report.json` | 协同报告、逐任务和逐交接解释、统计、来源 SHA-256 及运行版本 |
| `explanation.md` | 可读任务表、交接依据、维修网络 Mermaid 图及统计说明 |

配置参数：`--input`、`--output-dir`、`--max-combinations`。输出不能覆盖输入。退出码 0 为可行并成功导出，1 为不可行但诊断已导出，2 为输入、解析、配置、搜索上限或文件错误。

不可行时报告包含未匹配任务或拒绝原因，参与图为空，统计为 `null`。运行在相同目录时会替换之前的可行结果。输入或写入错误不保证生成完整的新产物，务必检查退出码，不把残留文件当成本次结果。并发运行请使用不同输出目录。

## 可解释性的范围

JSON 的 `evidence.tasks` 列出任务条件、命中规则 IRI、所需能力、候选、实际资源、能力供给、显式可用标记、响应时间及上限。证据直接取自同一次运行的合并图，不读取旧报告。

`evidence.transitions` 列出实际有序流程内及跨流程的相邻任务、发送和接收资源、方向授权、共同格式及 `canHandoffTo` 推导结果。若同一资源继续服务，会单独注明不要求自交接授权。未选择的任意资源对不冒充实际交接。

`constraint_evidence` 补充已选计划的数值对照：每项任务的响应及上限、相邻任务的结束/开始及等待间隔、每个实际资源的峰值并发与容量、耗材库存/预留/余量。所有时间单位为分钟。它是对现有协同判定和统计的解释，不重新筛选资源或搜索方案；没有可行计划时这些表为空，避免把失败请求呈现为已通过检查。

`collaboration` 保留原有容量/库存/时间冲突拒绝计数和最多五个失败组合示例；首个组合可行时自然没有失败示例，不代表其他组合均可行。解释是规则和输入事实的追溯，不是完整 OWL 证明或面向现实设备的认证。

可读报告也会显示未匹配任务、候选资源被排除的原因，以及已评估失败组合的具体信息。容量冲突显示资源、发生时刻、同时任务数与容量；库存冲突显示需要份数和库存份数；交接冲突显示发送与接收资源。一次组合可能违反多项约束，所以各原因的组合计数不能相加作为失败组合总数。没有候选时可能尚未枚举组合，不能将“失败组合为零”理解为计划可行。

`sources` 包括事实、两份模式、两份校验配置、三份规则、相关程序和依赖清单的 SHA-256。`runtime` 记录 Python 与 rdflib 版本。指纹有助于核查一次运行使用的本地文件，不构成依赖环境锁定或数字签名。

## 当前案例结果

- 4 个任务，6 条能力需求，4 条候选资源关系。
- 3 个已验证流程，4 个独立参与记录。
- 2 个串联、1 个并行、1 个全部后继执行的分支关系。
- 3 次实际跨资源交接有方向授权和共同报告格式。
- 网络历时 6 分钟，任务工时合计 8 分钟，峰值同时执行 2 个任务。
- 预留 1 份一次性检测试纸，不扣减真实库存。

统计口径见[维修流程统计与指标口径](维修流程统计与指标口径.md)。成本与质量仍没有输入数据，保持为明确缺失，不计算分数。

## 验收与边界

新增 6 项测试，核对解释与 RDF 一致、实际交接依据、来源指纹、成功后不可行结果覆盖、展示转义及输入保护/解析错误处理。累计 68 项测试通过；合并图的通用静态结构检查为 0 错误、0 警告。

随后补充数值证据与失败说明，新增 7 项测试，覆盖成功证据、容量冲突、库存不足、交接失败、无候选、任务等待及同资源延续。当前累计 75 项测试通过。例：重叠任务占用同一容量为 1 的检测仪时，报告显示 `active=2; capacity=1`；两项任务申请库存仅 1 份的试纸时，报告显示 `required_units=2; stock_units=1`，均不生成成功统计。

本阶段完成独立维修词表的统一运行和解释展示。程序没有加载 `killweb_ontology.ttl`，也未将维修词表与主本体声明等价；因此不能称为“主本体自动推出链网”。文章领域规则、评分执行和完整 OWL 一致性仍未完成。任务和依赖继续由事实输入，不从类声明自动创造任务。
